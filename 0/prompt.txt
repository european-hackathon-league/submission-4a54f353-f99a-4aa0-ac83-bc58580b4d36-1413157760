Major

Different customers with identical wording therefore collide. I checked the supplied spreadsheets: G70 has 4,000 verbatim IDs but only 3,993 exact texts. Seeding this design must either fail or discard records, breaking the promised counts and distinct-customer evidence. Fix: deduplicate ingestion by source-native record identity; keep content hashes non-unique. Handle duplicate evidence separately without deleting source identities.

Computing a comfort profile and then a budget profile overwrites the same value; a requirement spanning markets has the same ambiguity. Fix: derive requirement ranks for the requested weight profile, or store them keyed by requirement + weight profile. Explicitly define the context if `rank_score` is only a default-profile cache.

3. All-zero weights pass the documented validation. database-design.md:150-156 Eight zero weights satisfy “every weight ≥ 0,” but normalization then divides by zero. Fix: require a positive sum and finite numeric values; add a rejection test.
4. The overview still specifies one requirement per case, not per vehicle. README.md:10-11 For a case shared by G60 and G70, following this overview produces one requirement where the updated design requires one per confirmed vehicle. Fix: say “one per confirmed case and BMW line; optionally split by market.”

Phase 1 review
Reviewed [6dfc8e2](https://github.com/ghassenzaara/BMW-Product-Management-Challenge/commit/6dfc8e2) against phase 0. No review-fix commits yet.
Major

1. Audited writes are not guaranteed atomic. audit.py:153-168 The helper changes the row before writing its audit event, without starting a transaction or rejecting autocommit connections. Reproduced: inserting through an autocommit connection with an unknown actor raises `ValueError`, but leaves the row committed with zero audit events. Fix: wrap the mutation and audit insertion in one transaction/savepoint, and validate actor/key arguments before changing data. Test rollback when auditing fails.
2. The phase 0 source-identity defect is now enforced in SQL. 0003_records_and_config.sql:49-53 `content_hash` remains unique. With the documented source + normalized-text hash, distinct customers using identical wording collide. Reproduced: different record IDs with the same hash raise `UniqueViolation`; conflict-skipping would silently lose evidence. The supplied G70 data already contains repeated texts. Fix: preserve source-native record IDs and make the text hash a non-unique duplicate-detection index.
3. Existing embeddings cannot be refreshed. audit.py:229-234 Change detection compares audit-redacted values. Both old and new non-null embeddings become `<vector>`, so different vectors compare equal. Reproduced: replacing one feature vector with another leaves the old vector and writes no update event. Feature linking and later RAG reindexing would use stale vectors. Fix: compare actual values before redacting the audit payload; use array-aware equality for vectors.
4. The default test command breaks with the embedded database. conftest.py:24-36 `_with_db()` assumes a slash-delimited URL, but local `pgserver` returns PostgreSQL keyword connection info. It replaces part of the Unix socket directory instead of the database name. Reproduced: ordinary `uv run pytest` gives 5 passed, 9 setup errors. Supplying an equivalent encoded PostgreSQL URI through `TEST_DATABASE_URL`, without editing code, gives 14 passed. Fix: change databases with `psycopg.conninfo.make_conninfo(uri, dbname=name)`; test the default local setup and URLs with query parameters.
5. Raw evidence can be silently overwritten. storage.py:28-37 Local writes replace existing bytes; Supabase uploads explicitly enable upsert. Reproduced locally: writing different bytes to the same `raw_ref` replaces the original response. A refetch can therefore change the evidence behind an existing source record without preserving its original raw snapshot or recording that change. Fix: use immutable/versioned or content-addressed references; accept identical retries but reject different bytes at an existing reference.

Minor

6. Case IDs collide once the sequence reaches 10,000. 0005_signals_cases_requirements.sql:4-9 PostgreSQL `lpad(..., 4, ...)` truncates longer strings. Reproduced: sequence value 10,000 produces `CASE-1000`, colliding with an earlier case and preventing insertion. Fix: pad to a minimum width without truncating longer numbers; add a boundary test.
7. Strict-schema conversion silently removes dictionary contents. client.py:59-66 A field such as `extra: dict[str, str]` becomes an object with no properties and `additionalProperties: false`, allowing only `{}`. A future Signal extractor cannot return its intended extra metadata. Fix: explicitly reject unsupported open dictionaries or represent them as typed key/value entries; do not silently change their meaning.
